# UX improvements to consider

- `src/App.tsx` / `TagTree.tsx` / `SubtagTree.tsx`: switching the left panel between Folders/Tags/Subtags does not reset the active filter. `TagTree`'s and `SubtagTree`'s checkbox selection is local component state that unmounts (and visually resets) when you switch views, but the `tagFilter` closure it last pushed up to `App` stays applied to `TrackTable` until the newly-shown view happens to call `onFilterChange` itself. A user who filters by a Tag, then switches to Subtags, sees an unfiltered-looking Subtag tree (no subtag checked) while the table is silently still restricted to the old Tag's tracks — this looks like a bug and will cost real time to debug. Fix by having `App.tsx` reset `tagFilter` to "show all" whenever `leftView` changes.
- `src/components/TrackTable.tsx`: the only way to select multiple tracks for `BatchTagBar` is clicking each row's checkbox individually (plus a select-all-visible checkbox in the header). Add shift-click range select and cmd/ctrl-click toggle-add on rows, matching the checkbox state, since tagging 20+ tracks at once is a routine DJ workflow and one-by-one checkbox clicking is the single biggest friction point in the app.
- `src/components/BatchTagBar.tsx` and `FolderTree.tsx`'s context menu: bulk actions (add tag/subtag to checked tracks, "Analyse this folder", "Add all to queue" from a folder) give zero feedback that anything happened — the `<select>` just snaps back to its placeholder, or the context menu just closes. Add a brief toast/inline confirmation ("Tag added to 14 tracks", "23 tracks queued") so the user isn't left wondering if the click registered.
- `src/components/TrackTable.tsx`'s "Add all to queue" button (top of the table) queues every currently visible track with a single click and no confirmation — with no folder/tag filter active that's the entire collection. Add a confirmation dialog when the count exceeds some threshold (e.g. 50 tracks), since accidentally queuing thousands of tracks is easy to trigger and awkward to undo (no bulk "clear queue" exists either — see below).
- `src/components/PlaylistView.tsx`: there is no "clear queue" / "remove all" action — the only way to empty a long queue is removing tracks one at a time via each row's × button. Add a "Clear queue" button next to "Play next" in the queue header.
- `src/components/TrackTable.tsx`: when a search term or tag/subtag filter matches zero tracks, the table renders just an empty `<tbody>` under the header row — no "No tracks match" message. A first-time user typing a typo'd search sees a blank pane and can't tell if the collection failed to load or the filter is just too narrow.
- `src/components/FolderTree.tsx`, `TagTree.tsx`, and `TrackTable.tsx` all hide meaningful functionality (rename/delete/recolor a tag, per-folder analyse/queue, per-track play-next/analyse/show-in-folder) exclusively behind right-click context menus with no visual affordance (no "⋮" button, no hint text, no first-run tooltip) indicating they exist. A new user is unlikely to discover tag renaming or per-folder analysis at all. Add a small "⋮" icon button next to hoverable rows as a discoverable entry point into the same menu.
- `src/components/Toolbar.tsx`: the search box only matches `title`, `artist`, `album`, and `filename` (see `TrackTable.tsx`'s `visibleTracks` filter) — typing a tag or subtag name (e.g. "Techno") into search returns nothing, even though tags are prominently displayed as a table column. Either fold tag names into the search predicate or add placeholder text clarifying search doesn't cover tags.
- `src/components/TrackTable.tsx`: columns can be reordered by dragging headers but never hidden — anyone who doesn't care about the Format/Cloud/Status columns is stuck scrolling past them forever on every table row. Add a simple column-visibility toggle (e.g. a small "Columns" button in the toolbar row above the table, next to "Add all to queue") alongside the existing reorder/sort.
- `src/components/Toolbar.tsx`: "Update Collection" gives no loading feedback at all — no spinner, no disabled state, nothing — while `runScan()` (an async IPC call) is in flight. Since a directory scan is a common daily action and can take a few seconds on a big collection, add a spinner/disabled state on the button until the promise resolves, both to reassure the user it's working and to prevent an accidental double-click re-triggering the scan.
- `src/App.tsx`/`UndoToast.tsx`: genre/subgenre deletion shows an undo toast with a hardcoded 8-second auto-dismiss and no visual countdown (progress bar/ticking number). Users who look away for a moment lose the ability to undo a destructive delete with no warning it's about to disappear. Add a shrinking progress bar or countdown number to the toast.
- `src/components/Player.tsx`: the volume control is a single range slider with no quick-mute button — muting requires dragging to exactly 0 and remembering the previous level to restore it. Add a click-to-mute/unmute icon (with last-volume memory) next to the volume slider, a standard DJ-tool affordance.
- `src/components/TrackTable.tsx`: keyboard navigation only supports Arrow Up/Down to move the selected row one at a time; there's no Home/End or Page Up/Down for jumping around a large collection (thousands of tracks is the expected use case per the app's purpose). Add Home/End (jump to first/last visible row) and PageUp/PageDown (jump ~1 screen) to the same `handleKeyDown` effect.
- `src/state/store.ts`/`src/components/TrackTable.tsx`: sort column/direction is local `useState` in `TrackTable`, not persisted (unlike column order, which is saved via `setColumnOrder`/`loadColumnOrder`). Every app restart silently resets sorting back to Title/ascending even if the user always sorts by BPM or Key while prepping a set. Persist sort key/direction the same way column order already is.
- `src/components/TrackTable.tsx`: when analysis fails, the only feedback is a small red error icon in the Status column with a generic "Analysis failed" tooltip — there's no way to see *why* it failed (corrupt file, unsupported format, etc.) or any suggested next step beyond blindly re-running "Re-analyse track" from the context menu. Surface the actual error string (already available from the analysis pipeline, presumably logged) in the tooltip or in DetailPanel when that track is selected.
