# Session, 2026-10-08: releases 1.0.56–1.0.58, and a duplication and performance check

Releases **1.0.56** (PR #105: search in the Playlists box, a destination and tabs for Rekordbox
imports, a BPM switch in Similar tracks), **1.0.57** (PR #108: Convert to…, Tags suggested from
playlists, folders first) and **1.0.58** (PR #110: tempo measured over the whole track, resizable
panels, cue suggestions every 8 bars).

## Bars that drifted: the beat tracker's tempo
A 175 BPM tune was stored as 172.27 — the tracker can only report a few values on fast music.
Measurements and the fix: [research](../research/bpm-accuracy.md),
[ADR 0062](../adr/0062-tempo-measured-over-the-whole-track.md).

## A check for duplication and slow spots, from the code graph
The graph (Graphify, a dev tool proposed in PR #112, not merged at the time) listed 31
function names defined in more than one file. Each was read in the code; most are different
functions that share a name (`preciseTime` at two precisions, `applyDivision`, the trees'
`updateExpanded` and `applyFilter`). The graph shows structure, not speed: the slow spots came
from reading the code it pointed at.

Fixed:
- **Five toolbar buttons** (Audio, Cast, Mic, Record, Second screen) each carried the same
  popover code — open over the button, close on a click outside or Esc. Now
  `useToolbarPopover` (`src/components/useToolbarPopover.ts`); 154 lines gone.
- **Tracks looked up by scanning the list**: the queue view did `tracks.find` twice per queued
  track on every render, and the multi-row menu once per checked track. Now `tracksById`
  (`src/state/tracksById.ts`), one map per track list, shared. A rough timing in Node, 2,640
  tracks: about 2–13 ms per render of the lookups before (50–500 queued), about 0.2 ms after,
  building the map included. Small, but it was paid on every track-list change.
- **The track details read the track's playlists twice** (the Playlists section and the Tags'
  suggestions, added the same day): read once in `DetailPanel` and passed down.
- **A playlist's folder path** was built in four places: now `playlistFolders`
  (`src/state/savedPlaylist.ts`), used by the renderer and the main process.
- **Rekordbox's tree was flattened twice** (the import and the comparison), with the same
  " (2)" rule for repeated names: now `flattenRekordboxTree` (`rekordboxXml.ts`). The loose
  matching key was written twice in `playlists.ts`.
- **The Playlists box's menus** had the m3u export item and *Keep as my own* once for playlists
  and again for folders.

Left as they are:
- The Rekordbox import plan matches each path three times, and looks for songs at another path
  by scanning every file name per unmatched song (about 4 million checks on a 1,588-song
  import). Only when the import dialog opens.
- Convert runs one file at a time.
- "Artist - Title" labels are built in three places in the main process; accent folding in two
  (the playlist search and the tag suggestions); the two panel-width loaders in `App.tsx`.
- Two `getEssentia()` (`bpmKey.ts`, `energy.ts`): whether the second costs memory wasn't measured.

Not checked in the app: the five popovers after the change (open, close on outside click and
Esc, Cast's device search starting and stopping, Record's folder showing).
